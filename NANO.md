# nano-clone для cIos

Команда `nano` / `nano <файл>` в шелле. Реализовано на C
(`kernel/src/nano_c/nano.c` + `nano.h`), слинковано в ядро как
статическая библиотека через FFI-мост (`kernel/src/nano_ffi.rs`) и
безопасную Rust-обёртку (`kernel/src/nano.rs`, `nano::Editor`). Рендер
— `kernel/src/terminal.rs::draw_nano`/`draw_nano_panel`.

(Раньше существовала ещё и отдельная реализация на чистом Rust,
`nano`/`nanoc` были двумя параллельными командами — Rust-версию
удалили, `nanoc` переименовали в `nano`, теперь это одна реализация.)

## Почему это не "исходники nano, только скомпилированные"

Оригинальный nano.c требует то, чего в freestanding no_std ядре cIos
нет и в обозримом виде не будет:

- **ncurses/termios** — cIos рисует текст сам, напрямую в framebuffer
  (`text::draw_text`), а не через терминальный эмулятор с ANSI-кодами.
- **POSIX-файлы** — у cIos своя RAM-FS (`fs.rs`) с другим API.
- **fork/exec** — нужен для ^T (spellcheck через aspell) и линтера;
  в cIos вообще нет процессов.
- **regex.h, locale/gettext** — нет ни regex-движка, ни локализации.
- **libc/glibc** — на C-стороне используется свой минимальный
  freestanding-шим (`nanolibc.c`: memcpy/memset/strlen/malloc с
  заголовком размера — не настоящий libc).

Поэтому это заново написанный клон поведения и внешнего вида nano, а
не порт его C-кода. Экранная раскладка (title bar / тело / статус-строка
/ панель горячих клавиш) сделана по образцу
`winio.c::titlebar()/bottombars()` из оригинала.

## Упрощение: курсор и колонки — байтовые, не по Unicode-символам

Ради простоты C-кода 1 колонка курсора == 1 байт, а не 1 символ (как
было бы при честном UTF-8 char-boundary tracking). Шрифт cIos сейчас
всё равно запекает только ASCII 0x20..=0x7E (`font.rs`), так что на
практике разницы в поведении для реально отображаемого текста нет —
но при редактировании файла с не-ASCII байтами (например, кириллицей
в UTF-8) курсор и вставка/удаление будут смещаться на 1 байт за раз, а
не на 1 символ.

Позиция курсора (^C) — без процентов, только `line X/Y, col Z, char
A/B` (посчитать проценты — целочисленное деление-с-округлением через
самодельный `nl_utoa`, не стоило усложнения ради необязательной цифры).

## Что реализовано

Движение: стрелки, ^B/^F/^P/^N, ^A/Home, ^E/End, PgUp/PgDn (^Y/^V),
^Left/^Right (прыжок по словам), Del/^D, Backspace/^H.

Редактирование: вставка символов, Enter, Tab, indent/unindent
(M-}/M-{).

Пометка и вырезание: ^^ / M-A (Mark), ^K (вырезать строку целиком —
или помеченный регион, если Mark активен; несколько ^K подряд
накапливаются в один буфер вставки, как в оригинале), ^U (вставить).

Поиск/замена: ^W (Search, без учёта регистра, с переносом в начало
буфера), M-W (повторить поиск), ^\\ (Replace — **упрощено**: заменяет
ВСЕ вхождения сразу, без пошагового подтверждения Yes/No/All/Cancel,
как в оригинале).

Прочее: ^_ (Go To Line[,Column]), ^R (Read File — вставляет файл в
позицию курсора), ^J (Justify — переносит абзац; **упрощено**:
фиксированная ширина в 72 символа вместо реальной ширины окна), ^C
(позиция курсора), ^O (сохранить, с запросом имени для нового файла),
^X (выход, с диалогом Save modified buffer? Y/N/^C), ^G (экран
справки), ^L (no-op "Refreshed" — полный кадр и так перерисовывается
по мере надобности).

## Осознанно не реализовано

- **^T spellcheck/linter** — нужен внешний процесс, в cIos их нет.
- **Переключение в regex-поиск (M-R)** — нет regex-движка. Обычный
  (не-regex) поиск в самом nano и без этого не требует regex — это
  подтверждено в `search.c` оригинала (`ISSET(USE_REGEXP)`), так что
  сам факт поиска здесь есть, просто без regex-режима.
- **Undo/redo (M-U/M-E)** и **мультибуферы (M-F, M-</M->)**.
- Более редкие переключатели: мышь, suspend, softwrap, DOS/Mac
  переводы строк, backup-файлы, execute-command, word count (M-D),
  автодополнение (^]), парная скобка (M-]), комментирование (M-3).
  Можно добавить по мере надобности — архитектурно ничего не мешает.

## Известные упрощения рендера

- Заголовок центрируется проще, чем в оригинале (без многоточия при
  обрезании длинных путей).
- Горизонтальная прокрутка длинных строк есть (с `$` по краям, как в
  оригинале), но управляется общим смещением курсора, а не отдельно на
  строку.
- Шрифт cIos сейчас запекает только ASCII 0x20..=0x7E (см. `font.rs`)
  — кириллица и вообще всё не-ASCII в тексте не отрисуется (будет
  "дыркой"), это ограничение всей ОС, а не отдельно nano-режима.

## Архитектура моста

```
main.rs / terminal.rs  (Rust, как обычно)
        │  вызывает методы nano::Editor (safe-обёртка)
        ▼
kernel/src/nano.rs      -- extern "C" объявления + безопасная обёртка
        │  вызывает nano_open/nano_handle_key/nano_line/...
        ▼
kernel/src/nano_c/nano.c + nano.h   -- вся логика редактора на C
        │  вызывает cios_alloc/cios_free/cios_fs_read/cios_fs_write
        ▼
kernel/src/nano_ffi.rs  -- extern "C" fn на стороне Rust: тот же
                            глобальный аллокатор ядра (memory.rs) и fs::
```

`kernel/build.rs` компилирует `nano_c/nano.c` + `nano_c/nanolibc.c` и
линкует как `libnano_c.a` в конечный `cios-kernel` ELF — никакого
отдельного шага руками не нужно, обычный `cargo build --release`
(через `make kernel`) соберёт и C, и Rust. (Каталог с C-исходниками
по-прежнему называется `nano_c/` — это просто "здесь лежит C-код", а
не название команды; переименование команды `nanoc` → `nano` этого
не касалось.)

## Модель памяти / безопасность

- У C и Rust **одна общая куча** — `cios_alloc`/`cios_free`
  (`nano_ffi.rs`) дёргают тот же глобальный аллокатор ядра
  (`linked_list_allocator`, `memory.rs`), никакой отдельной арены для C
  не заведено.
- `nl_malloc`/`nl_free`/`nl_realloc` (`nanolibc.c`) прячут размер блока
  в 8-байтовом заголовке перед возвращаемым указателем — весь остальной
  `nano.c` из-за этого вообще не думает о размерах при освобождении
  памяти (иначе один неверный размер при `cios_free()` — это порча
  кучи, не просто утечка).
- **Важное отдельное исключение**: буфер от `cios_fs_read()` НЕ имеет
  такого заголовка (он выделяется прямо в `nano_ffi.rs` под точный
  размер файла) — освобождать его нужно ровно `cios_free(ptr, len)`, **не**
  `nl_free(ptr)`. Это явно прокомментировано в трёх местах (`nano.h`,
  `nano.c`, `nano_ffi.rs`) именно потому, что перепутать легко, а
  последствия — молчаливая порча кучи, не сразу видимый краш.
- Код выполняется в основном цикле ядра с включёнными прерываниями
  (см. `interrupts.rs`) — отсюда обязательные флаги сборки
  `-mno-red-zone`/`-mcmodel=kernel`/`-mgeneral-regs-only`, см. `build.rs`.
  Без `-mno-red-zone` в частности возможна редкая порча стека от
  асинхронного прерывания, пока leaf-функция C использует red zone.

## Как собрать

Ничего специально делать не нужно — `make kernel` (или `cargo build
--release` внутри `kernel/`) дополнительно:
1. запускает `kernel/build.rs`, который через crate `cc` компилирует
   `nano_c/nano.c` + `nano_c/nanolibc.c` обычным системным `cc`
   (`gcc`/`clang` — не кросс-компилятором: несмотря на имя таргета
   `x86_64-unknown-none`, это та же архитектура x86_64, кросс-компилятор
   не нужен, см. комментарий в `build.rs`);
2. линкует получившуюся `libnano_c.a` в `cios-kernel` как обычно для
   `[build-dependencies] cc`.

Требование: на машине, где собирается ядро, должен быть системный
C-компилятор (`cc`/`gcc`/`clang`) в `PATH`, помимо Rust-тулчейна.

## CI

`.github/workflows/build.yml` собирает ядро (`make kernel`) отдельной
джобой (`build-kernel-clang`) с `CC=clang`, в дополнение к основной
сборке ISO на gcc — проверка сразу на двух компиляторах.

## Проверено сборкой

Первый реальный прогон CI (оба компилятора) нашёл ровно одну ошибку в
этом коде: отсутствующую декларацию `cios_free` в `nano.c` (см. историю
изменений) — на gcc это было лишь предупреждение
(`-Wimplicit-function-declaration` там не фатален по умолчанию), на
clang — уже жёсткая ошибка сборки. Поправлено.

Важное следствие: раз Rust-сторона (`nano.rs`) при этом скомпилировалась
без единой ошибки, это заодно подтверждает риск, который раньше был
открытым — имена вариантов `pc_keyboard::KeyCode::Home/End/PageUp/
PageDown/Delete`, используемые в `nano.rs`, оказались верными (иначе
компилятор сообщил бы об этом отдельной ошибкой типов, как это
произошло для несвязанной проблемы в `bitmap.rs` в этом же прогоне).

Что всё ещё не подтверждено: полный успешный `make iso` от начала до
конца и реальная загрузка/работа редактора в QEMU — оба этих пункта
ждут следующего прогона.

## Новые/изменённые файлы (относительно состояния без nano)

- `kernel/src/nano_c/nano.h`, `nano.c` — публичный API и вся логика
  редактора.
- `kernel/src/nano_c/nanolibc.h`, `nanolibc.c` — минимальный
  freestanding-шим (`memcpy`/`memset`/`strlen`/... + malloc с
  заголовком размера).
- `kernel/src/nano_ffi.rs` — `extern "C"` мост Rust → C (аллокатор, fs).
- `kernel/src/nano.rs` — безопасная Rust-обёртка (`nano::Editor`),
  используется из `main.rs`/`terminal.rs`.
- `kernel/build.rs` — сборка C-файлов через crate `cc`.
- `kernel/Cargo.toml` — `[build-dependencies] cc`.
- `kernel/src/fs.rs` — `fs::write()` (создать-или-перезаписать файл),
  нужна для ^O.
- `kernel/src/keyboard_queue.rs` — хранит не просто `DecodedKey`, а
  `KeyEvent{ key, ctrl, alt }`.
- `kernel/src/interrupts.rs` — трекает состояние Ctrl/Alt напрямую по
  сырым PS/2 скан-кодам (Set 1), независимо от `pc_keyboard`, потому
  что тот с `HandleControl::Ignore` не превращает Ctrl+буква в
  управляющий байт — а почти все хоткеи nano это Ctrl+буква.
- `main.rs` (`Mode::Nano`, команда `nano`), `terminal.rs`
  (`draw_nano`/`draw_nano_panel`), `shell.rs` (`nano` в списке команд).
