# nano-clone для cIos — версия на C

Команда `nanoc [файл]` в шелле (существует параллельно с `nano` —
Rust-версией, см. NANO.md; обе доступны одновременно, ничего не
заменяет друг друга).

## Что это

То же самое зеркало поведения/раскладки GNU nano, что и `nano.rs`, но
реализованное на C и слинкованное в ядро как статическая библиотека
через FFI. Возможности и осознанные исключения — **ровно те же**, что
у Rust-версии (см. список в NANO.md: без ^T, без regex-поиска, без
undo/redo, без мультибуферов). Не дублирую тут этот список — отличия
именно этой, C, реализации перечислены ниже.

## Архитектура моста

```
main.rs / terminal.rs  (Rust, как обычно)
        │  вызывает методы nano_c::Editor (safe-обёртка)
        ▼
kernel/src/nano_c.rs    -- extern "C" объявления + безопасная обёртка
        │  вызывает nano_open/nano_handle_key/nano_line/...
        ▼
kernel/src/nano_c/nano.c + nano.h   -- вся логика редактора на C
        │  вызывает cios_alloc/cios_free/cios_fs_read/cios_fs_write
        ▼
kernel/src/nano_ffi.rs  -- extern "C" fn на стороне Rust: тот же
                            глобальный аллокатор ядра (memory.rs) и fs::
```

`kernel/build.rs` компилирует `nano_c/nano.c` + `nano_c/nanolibc.c` и
линкует как `libnano_c.a` в конечный `cios-kernel` ELF — никакого
отдельного шага руками не нужно, обычный `cargo build --release`
(через `make kernel`) соберёт и C, и Rust.

## Отличия ОТ Rust-версии (nano.rs)

- **Колонка курсора — байтовая, не по Unicode-символам.** В Rust-версии
  из-за UTF-8 это разные вещи (char boundary tracking); здесь ради
  простоты C-кода 1 колонка == 1 байт. Шрифт cIos всё равно рисует
  только ASCII 0x20..=0x7E (`font.rs`), так что на практике разницы в
  поведении для реально отображаемого текста нет — но при редактировании
  файла с не-ASCII байтами (например, кириллицей в UTF-8) курсор и
  вставка/удаление в C-версии будут смещаться на 1 байт за раз, а не на
  1 символ, в отличие от `nano.rs`.
- **Позиция курсора (^C) без процентов** — только `line X/Y, col Z, char
  A/B`, без `(N%)`, которые есть в `nano.rs`. Чтобы их посчитать, нужно
  целочисленное деление-с-округлением через самодельный `nl_utoa`, не
  стоило усложнения ради необязательной цифры.
- Память управляется вручную (malloc/free с спрятанным заголовком
  размера в `nanolibc.c`, см. комментарии там) — в Rust-версии всё это
  даёт бесплатно `Vec`/`String`/`Drop`. Вычитано вручную (нет
  инструментов вроде Miri/ASan в этой песочнице, см. ниже), но это
  реальная категория риска, которой у `nano.rs` в принципе нет.

## Модель памяти / безопасность

- У C и Rust **одна общая куча** — `cios_alloc`/`cios_free`
  (`nano_ffi.rs`) дёргают тот же глобальный аллокатор ядра
  (`linked_list_allocator`, `memory.rs`), никакой отдельной арены для C
  не заведено.
- `nl_malloc`/`nl_free`/`nl_realloc` (`nanolibc.c`) прячут размер блока
  в 8-байтовом заголовке перед возвращаемым указателем — весь остальной
  `nano.c` из-за этого вообще не думает о размерах при освобождении
  памяти (иначе один неверный размер при `cios_free()` — это порча
  кучи, не просто утечка).
- **Важное отдельное исключение**: буфер от `cios_fs_read()` НЕ имеет
  такого заголовка (он выделяется прямо в `nano_ffi.rs` под точный
  размер файла) — освобождать его нужно ровно `cios_free(ptr, len)`, **не**
  `nl_free(ptr)`. Это явно прокомментировано в трёх местах (`nano.h`,
  `nano.c`, `nano_ffi.rs`) именно потому, что перепутать легко, а
  последствия — молчаливая порча кучи, не сразу видимый краш.
- Код выполняется в основном цикле ядра с включёнными прерываниями
  (см. `interrupts.rs`) — отсюда обязательные флаги сборки
  `-mno-red-zone`/`-mcmodel=kernel`/`-mgeneral-regs-only`, см. `build.rs`.
  Без `-mno-red-zone` в частности возможна редкая порча стека от
  асинхронного прерывания, пока leaf-функция C использует red zone.

## Как собрать

Ничего специально делать не нужно — `make kernel` (или `cargo build
--release` внутри `kernel/`) теперь дополнительно:
1. запускает `kernel/build.rs`, который через crate `cc` компилирует
   `nano_c/nano.c` + `nano_c/nanolibc.c` обычным системным `cc`
   (`gcc`/`clang` — **не** кросс-компилятором, см. комментарий в
   `build.rs` про то, почему имя таргета `x86_64-unknown-none` тут не
   должно вводить в заблуждение: это та же архитектура x86_64, кросс-
   компилятор не нужен);
2. линкует получившуюся `libnano_c.a` в `cios-kernel` как обычно для
   `[build-dependencies] cc`.

**Новое требование по сравнению с состоянием до этого изменения**: на
машине, где собирается ядро, теперь должен быть системный C-компилятор
(`cc`/`gcc`/`clang`) в `PATH`, помимо Rust-тулчейна. Раньше проект был
чисто на Rust и этого не требовал.

## CI

`.github/workflows/build.yml` теперь собирает ядро (`make kernel`) ещё
и с `CC=clang` отдельной джобой (`build-kernel-clang`), в дополнение к
основной сборке ISO на gcc — раз этот C-код никогда не гонялся ни
через один компилятор до этого, лучше проверить сразу на обоих, чем
один раз и понадеяться.

## Не проверено сборкой (как и вся nano.rs-версия)

В песочнице, где это писалось, нет ни сети, ни Rust-тулчейна, ни
C-компилятора — собрать не удалось ни разу, ни на каком этапе. Код
вычитан вручную настолько внимательно, насколько это в принципе
возможно без компилятора (типы, границы массивов, работа с памятью,
контроль владения в `insert_lines_at_cursor`/`cut_region`/`do_justify` —
самые рискованные места), но это НЕ замена настоящей сборке и
тестированию. Отдельные конкретные риски:

- `pc_keyboard::KeyCode::Home/End/PageUp/PageDown/Delete` в
  `nano_c.rs` — те же непроверенные имена вариантов, что и в
  `nano.rs` (см. NANO.md), не новый риск, но и не устранённый.
- `cc`-крейт может не найти подходящий компилятор на непривычных
  платформах (см. `build.rs`) — на обычном Linux/macOS с установленным
  `gcc`/`clang` в `PATH` должно работать сразу, дальше не
  перепроверялось.
- `-mgeneral-regs-only`/`-mcmodel=kernel` поддерживаются GCC и clang,
  но не перепроверялись на КОНКРЕТНОЙ версии компилятора — если сборка
  падает именно на одном из этих флагов, можно временно убрать его из
  `build.rs` (`-mcmodel=kernel` убирать не стоит — см. объяснение в
  `build.rs`, без него релокации для адреса `0xffffffff80000000` будут
  в принципе неверными).

## Новые файлы

- `kernel/src/nano_c/nano.h`, `nano.c` — публичный API и вся логика
  редактора.
- `kernel/src/nano_c/nanolibc.h`, `nanolibc.c` — минимальный
  freestanding-шим (`memcpy`/`memset`/`strlen`/... + malloc с
  заголовком размера).
- `kernel/src/nano_ffi.rs` — `extern "C"` мост Rust → C (аллокатор, fs).
- `kernel/src/nano_c.rs` — безопасная Rust-обёртка (`nano_c::Editor`),
  используется из `main.rs`/`terminal.rs` так же, как `nano::Editor`.
- `kernel/build.rs` — сборка C-файлов через crate `cc`.
- Правки: `kernel/Cargo.toml` (`[build-dependencies] cc`), `main.rs`
  (`Mode::NanoC`, команда `nanoc`), `terminal.rs`
  (`draw_nano_c`/`draw_nano_c_panel`), `shell.rs` (`nanoc` в списке команд).
